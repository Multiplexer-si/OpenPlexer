# Onboarding design

Phase 6 gives a developer one command to join a project. It also limits how long a laptop can act on policy it has not confirmed with the hub. The Go hub and the Cloudflare Worker share the invite and member status APIs. The same laptop commands work with either hub. [Phase 5 design](cloudflare-hub-design.md)

Issue #91 records the design for milestone 8. The numbered sections name the issues that build it.

## 1. Invite contract (#92)

An invite binds one existing project, one new team member ID, and one hub role, `member` or `lead`. The default is `member`. The project selects the repository, policy, and Room for the new home. The credential follows the existing team-wide roster rules. For example, an invited lead has team-wide admin access. Show the hub role and project before a lead issues an invite. [Hub HTTP API](hub.md#http-api)

Both hubs serve these routes. In the table, `admin` means `/api/v1/admin`, and all admin routes require a lead bearer. An invite has a public `id` and a separate random code. The `invite` object contains `id`, `project_id`, `member_id`, `hub_role`, `require_approval`, `state`, `created_at`, and `expires_at`. Timestamps are UTC RFC 3339. An invite code is a one-use enrollment secret. The member bearer is the separate credential described in section 2.

| Method and path | Request | Success | Other results |
|---|---|---|---|
| `POST admin/invites` | `{project_id, member_id, hub_role?, expires_in_seconds?, require_approval?}`. Approval defaults to false. | `201` with `{invite, code}`. The hub returns the code once. | `404` for an unknown project. `409` for an occupied member ID, a live invite for that ID, or the live invite limit. |
| `GET admin/invites` | Optional `after=<id>` and `limit=<n>`. No body. | `200` with `{invites, next_cursor}`. A finished page has a null cursor. | `400` for invalid, repeated, or unknown query parameters. A cursor can outlive its row. |
| `DELETE admin/invites/{id}` | No body. | `200` with `{invite}` in `revoked`. A repeat returns the same state. | `404` for an unknown ID. `409` if redeemed or expired. |
| `POST admin/invites/{id}/approve` | No body. | `200` with `{invite}` in `approved` or, for an approval retry after redemption, `redeemed`. | `404` for an unknown ID. `409` when there is no request to approve, approval is disabled, or the invite is revoked or expired. |
| `POST /api/v1/invites/redeem` | `{code, token_hash}`. The code authorizes this request. | `200` with `{state: "redeemed", project_id, repo, member_id, hub_role}`. `202` with `{state: "pending_approval", invite_id}` and `Retry-After: 5` while approval is pending. | `404` for an unknown code, `410` for a known expired or revoked code, `409` for a competing claim, a spent code, or a roster conflict. |

Use `Cache-Control: no-store`. Return the existing `{"error":"..."}` envelope. Require one valid bearer header on admin requests. Use `401` with `WWW-Authenticate: Bearer` for an invalid or revoked bearer, `403` for a non-lead, and `405` with `Allow` for a wrong method. Use `400` for invalid JSON, repeated or unknown fields, malformed IDs or codes, invalid ranges, or an unexpected body. Use `413` for a body over 64 KiB and `500` when state is unavailable. `HEAD` on the list follows `GET` without the body. Lead and invite commands refuse redirects and require HTTPS off loopback. [Phase 5 HTTP contract](cloudflare-hub-design.md#5-http-contract)

Reuse the hub's ID syntax for member and project IDs. Generate public invite IDs as 32 lowercase hex characters and codes as 32 random bytes in unpadded base64url. Store the code's SHA-256 over the encoded string. Keep one live invite per member ID and up to 1,024 live invites per team. Expiry defaults to 48 hours and accepts whole seconds from 60 through 604,800. The hub clock decides expiry at `now >= expires_at`. List up to 100 results per page in public ID order, strictly after the cursor. The default page size is 100. Each page reads current state. Keep terminal rows for 30 days from redemption, revocation, or expiry, then purge them during maintenance. Retain the audit records under the existing audit rules.

| State | Transition |
|---|---|
| `issued` | Create enters this state. With approval off, the first valid redeem goes straight to `redeemed`. With approval on, it binds the submitted hash and moves to `pending_approval`. |
| `pending_approval` | The same hash can poll and gets `202`. A different hash gets `409`. A lead can approve or revoke. |
| `approved` | The bound hash can redeem. A lead can still revoke before redemption. |
| `redeemed` | The member is in the roster. The matching retry in section 2 returns the original receipt. Any other claim gets `409`. |
| `revoked` or `expired` | Terminal. A live state can be revoked by a lead or expires at the original deadline. Expiry also applies while approval is pending. |

Approval authorizes the claim bound to the invite. Before approval, ask the intended recipient over a trusted channel to confirm that their own `join` reports `pending_approval` for the same public invite ID. The member ID identifies the intended roster entry. The lead relies on the recipient's confirmation to identify the claimant. If the recipient gets a conflict or cannot confirm, revoke and reissue. The redemption status codes expose invite state to someone who already knows the code.

Check the project, invite state, member ID, and token hash uniqueness at the committing write. Reserve the member ID for the live invite so a direct roster addition for that ID returns a conflict. In Go, use the data-folder lock and atomic snapshot write. In the Worker, use the team object's SQLite transaction. Commit roster insertion, consumption, and audit together. Write `invite.created`, `invite.requested`, `invite.approved`, `invite.revoked`, and `invite.redeemed` once at the corresponding transitions. Target `invite:<id>` with project, member ID, and hub role in metadata. Admin actions name the lead, and the request and redeem name the bound member ID without asserting a verified human identity. Also write the existing `member.added` on redemption, with a null admin actor and the invite ID in metadata. Expiry is derived from the deadline and adds no chain record. Keep the code, bearer, hashes, and full link out of audit and application logs. [Audit format](../spec/audit/README.md)

Use `openplexer-hub invite create|list|approve|revoke`. `create` takes `--project`, `--member`, optional `--role`, `--expires-in`, and `--require-approval`. `approve` and `revoke` take `--id`. The Go data-folder commands call the same operations under the store lock and trust the operator who can write the folder. Audit records for those admin actions have a null actor. Local creation takes `--origin` for the link and uses the folder's policy keys. Remote commands use `--hub` and the existing private `--token-file` or stdin. They call these endpoints on either hub and use the same output format. The create command prints the link from section 3 or saves it to a new private file. The laptop redeems over HTTP for either hub.

The TypeScript reference at `7d80045a` records workspace invites by email address. It enrolls a matching account in the same transaction if one already exists. Otherwise, a later sign-in with the matching email can accept the invite. A configured sign-in provider supplies that address. Mail delivery is optional and belongs to the separate email-link sign-in flow. OpenPlexer's short-lived code lets a lead use the team's existing private channel. A project-only credential would change authorization throughout the hub. This milestone uses the current roster and makes the team-wide reach visible at issuance.

## 2. Token creation and retries (#92, #95)

For a new join, the laptop draws 32 random bytes and encodes them as unpadded base64url, in the existing roster bearer format. It saves that bearer in owner-only pending state before the first redeem POST. The request sends `token_hash`, 64 lowercase hex characters of SHA-256 over the encoded bearer. The member bearer stays out of links and all responses. Only ordinary authenticated requests after redemption send it in `Authorization: Bearer`. The hub keeps the digest in the roster. If the lead loses the invite creation response, they can list, revoke, and reissue the invite.

Bind pending state to the origin, invite code digest, and intended home. Store it atomically under a per-home lock. A retry loads the same bearer and sends the same hash. This covers an interrupted request, a lost `202` or `200`, and restart after lead approval. Pending state can keep the planned join and nonsecret receipt data without storing the link. The CLI can retry `202` at most once per `Retry-After` interval, or exit with a command to rerun without echoing the link.

Give each roster entry an internal enrollment ID. Assign one to existing entries on upgrade. Assign a fresh ID on every roster insertion and token replacement, even if the same member ID and token hash return. Save the enrollment ID with the redemption receipt in the same commit.

After redemption, allow the same code and hash to retrieve the original receipt for 24 hours from the commit, even if the original invite deadline passes. Require the active roster entry to match the receipt's enrollment ID, member ID, role, and token hash. A mismatch or a missing entry gets `409`. A retry changes no roster, invite, or audit state. If the receipt window closes before the laptop can finish an interrupted join, the lead can check the roster and provision a replacement after revoking the old credential. A revoked or expired live invite requires a new link.

The existing `add-member` commands generate the bearer on the hub side. Applying that flow to join would require returning a secret on first use and could strand the laptop after a lost response. Saving the bearer before redeem makes the same credential available for every retry.

## 3. Link, key trust, and join (#95)

Use `openplexer join 'https://hub.example.com/join/<code>#fp=<fingerprint>'`. The lead sends the link through a trusted private channel. The fragment holds the trust value and stays on the client when a URL is used over HTTP. `join` parses the link locally. It accepts the exact path shape and fragment, with no user info or query. It takes the origin from the link, requires HTTPS off loopback, and refuses redirects. It sends the code only in the redeem POST body. The join path is a CLI link and has no browser handler. A user who opens it in a browser can expose the code to access logs. The guides tell leads and members to paste it only into `join` and treat it as a secret until spent.

Pin `GET /.well-known/jwks.json`, the hub's policy verification keys. The checkpoint keys have their own trust path. Compute the fingerprint as lowercase hex SHA-256 over canonical UTF-8 JSON of `{"keys":[...]}`. For each key keep exactly `kty`, `crv`, `kid`, `x`, and `y`. Sort the keys by `kid` in UTF-8 byte order before canonical encoding. Cap the JWKS at the existing 64 KiB sync limit and validate all keys first. Require a nonempty set of public P-256 keys, unique nonempty `kid` values, strict base64url coordinates, and valid curve points. Reject repeated JSON object names and private key material. If present, `alg` must be `ES256`, `use` must be `sig`, and `key_ops` must be `["verify"]`. Pin the normalized keys used in the hash, so reordering or pretty printing leaves the fingerprint unchanged. The lead CLI uses its trusted data folder or the configured HTTPS hub's policy JWKS. The dashboard uses the same normalization. [Canonical JSON](../spec/canonical-json/README.md) · [Policy JWS verification](../spec/policy/README.md#the-signed-bundle)

1. Resolve the checkout and check for a conflicting home as in section 5. Fetch and check the public JWKS against `fp` before redeeming or sending a member bearer. Stop on any mismatch. Get any replacement fingerprint through the trusted channel.
2. Reserve the root, save or resume the pending bearer, and redeem. On `202`, report `pending_approval` and the public invite ID for the recipient to confirm with the lead. On `410`, clear the pending bearer and root reservation so the user can join with a new invite. On `200`, take the project, repo, member ID, and hub role from the receipt. Write the usual private configuration and pinned keys into a staged home. Use the normal sync path to verify the signed bundle against the advertised and pinned keys, check its project and repo against the receipt, and apply the version floor. During join, require the advertised set still to match `fp`. Stop if it changed during enrollment.
3. Publish the home and its registry entry only after initial sync succeeds. Rename the staged home into place, then register it under the registry lock. A retry recognizes the same home if interrupted between those two writes, preserves the floor, and completes registration. An existing different home is an error. If policy is absent, invalid, or unavailable, preserve the private pending state for a retry. A retry after a finished join to the same home uses the saved enrollment identity and checks policy without creating a second member.
4. Print the project, member, hub role, policy version, and effective policy grants or the absence of a policy role. Offer the supported project hook and user daemon service after sync. Use explicit consent or explicit flags for changes. A declined or unsuccessful optional install leaves a usable joined home. In noninteractive mode, print the follow-up commands. The user still reviews and trusts the project's hook in their agent.

On the Worker, stage the new policy key first. Staging adds its public JWK and changes the set fingerprint. Distribute the staged keys over the trusted channel and update existing homes with `configure --keys` before activation. Activate the new key and publish a higher policy version signed by it. Issue new links with the fingerprint of the staged set, which remains the same through activation because the retired public key stays advertised. An old link with the previous fingerprint fails before redemption if the set changed. Give the member a newer trusted link. For an already claimed or consumed invite within its recovery window, the lead can refresh the fingerprint on the same original link so the pending bearer can resume. For a lost original link, use the revoke and recovery rules in sections 1 and 2. The same mismatch rule applies when a Go operator replaces the policy key set. [Phase 5 rotation](cloudflare-hub-design.md#4-keys)

Trust on first use would let a substituted hub supply its own keys. Pinning one active key would also require a separate pin during planned rotation. Pinning the validated set lets the lead distribute staged keys before switching signers. A trusted link authenticates the initial set. It also relies on the lead's private delivery of the origin and enrollment code.

## 4. Policy role (#92, #95)

An invite carries a hub role only. Start with a signed project bundle that can be synced. Use a fresh member ID, or remove any old role assignments and temporary grants for that ID from published project bundles before reusing it. The member redeems the invite and enters the roster. The lead then assigns the member a policy role in `members` and publishes a higher bundle version. Both hubs require the member to exist in the roster at publication. The hub signs the authorized publication. The Go data-folder operator can also publish.

If the first sync comes before the grant, `join` shows the current policy version and no policy role. The signed policy's defaults apply. The gate denies writes and pushes that require a grant. A subsequent `policy sync` or daemon sync picks up the higher version once the lead publishes it. If the lead publishes before the first sync, `join` shows the role and grants from that version. [Policy evaluation](../spec/policy/README.md#evaluation)

A role hint in the invite could become stale between issuance and join. Redeeming and then editing or signing policy on the member's behalf would give enrollment permission to change grants. Keeping publication explicit lets the lead review and audit the policy change as one operation.

## 5. Home selection and portable hooks (#93, #95)

Keep an owner-only registry at `~/.openplexer/projects.json`. It maps canonical absolute checkout roots to canonical absolute OpenPlexer homes. `join` uses the nearest Git checkout root by default, including linked worktrees, or an explicit `--project-root`. Use `--home` to select an explicit home. Otherwise put each joined home under `~/.openplexer/homes/` using the hex SHA-256 of the canonical root path as the directory name. `openplexer configure --project-root <dir>` registers an existing configured home after validating the path and home. Resolve symlinks and check directory identity before writing. The registry holds paths only. Update it under a lock by atomic rename. Reserve pending joins by root in private local state so concurrent joins cannot spend two invites for one root.

`openplexer install claude-code --project . --portable` and the matching Codex command write these hook commands in the existing project hook files and register the current home. Teams can commit the hook files with those entries.

```sh
openplexer hook claude-code pre-tool --project-home
openplexer hook codex pre-tool --project-home
```

For `--project-home`, resolve each covered write target against the agent's input `cwd`. Resolve symlinks, including existing parents of a new file. For each resolved target, select its deepest registered ancestor on directory boundaries. Evaluate the path relative to that root with the selected home's policy. A call from an outer checkout can therefore use the inner checkout's policy for one target and the outer policy for another. A denial on any target blocks the whole call. Use the resolved `cwd` for covered shell execution checks. If a call has both write and execution checks, all must pass.

An unregistered nested repository uses the registered outer root. A separately registered nested checkout uses its own home. Git worktree roots are separate checkout roots and can be registered individually. If the registry is missing or unreadable, the selected home is missing, or a covered check has no matching root, return the agent's blocking result and give the join or registration command. Refuse a second home claiming the same root. If hand edits introduce duplicate claims, block the affected checkout until the registry is repaired. The portable hook does not select via `OPENPLEXER_HOME` or fall back to another home. Keep the legacy hook entry and home selection for users who omit `--portable`. Normal CLI commands with no explicit home can use the registered root lookup from `cwd` before the legacy default. Guard the registry and every selected home in hook path checks.

Project-local home pointers would let a checkout choose a different trusted configuration. Committing the lead's executable path or a developer's home would break on teammates' machines. A command on `PATH` and a user-owned registry let each laptop select its own home. Agents must be able to find the installed binary on their `PATH`. The Codex runtime's behavior when a hook executable cannot start still applies. [Claude Code hooks](hooks-claude-code.md) · [Codex hooks](hooks-codex.md)

## 6. User daemon service (#94)

Run one user service per OpenPlexer home. `openplexer service install|uninstall|status` selects the registered home for the checkout or accepts `--home <dir>`. Installation checks that the home has a valid hub configuration. Name the service using the full hex SHA-256 of its canonical home path. Two checkouts that share one home use one service. The same daemon lock used by `openplexer daemon` prevents a manual process and a managed process from running the same home at once. If a foreground daemon already holds the lock, tell the user to stop it before starting the service.

| Platform | Service | Logs |
|---|---|---|
| macOS | Write `~/Library/LaunchAgents/com.openplexer.daemon.<hash>.plist`. Use `RunAtLoad` and `KeepAlive`. Load the agent into the current user's GUI domain. | Put output and errors in owner-only files under `<home>/logs/`. Give the paths and the procedure for rotation in the guide. |
| Linux | Write `~/.config/systemd/user/openplexer-daemon-<hash>.service`, honoring the user's systemd config directory. Use `Restart=always` and `RestartSec=5s`. Enable and start with `systemctl --user`. | Use the user journal and print the matching `journalctl --user -u` command. |

Both services run the absolute installed binary with `daemon --quiet` and pass the home as `OPENPLEXER_HOME` in the service environment. They contain no bearer or invite code. Quiet mode reports operational errors and suppresses Room event bodies. The foreground daemon keeps its existing Room output by default. Install is idempotent and reports start errors. Uninstall stops and disables the matching service before removing its file. It preserves the home, logs, policy, and cursor. Status reports the selected home and whether the service is missing, running, stopped, or failed. It shows recent manager failure information, the log location, and local policy status. It distinguishes a running process from a fresh policy. Service startup requires the user's service manager. #100 explains login and Linux lingering for teams that need operation after logout.

One supervisor for all homes would have to watch the registry, manage multiple daemons, and restart each independently. Per-home services give each project independent startup and logs. The existing system service for the Go hub is a separate operator task. [Self-host the hub](self-host.md#install-the-service)

## 7. Policy age and the gate (#96)

Use a laptop freshness limit for hub-connected homes. Store `max_policy_age_seconds` in the private home config. Default to 300 seconds, including for existing hub-connected homes on upgrade. `configure --max-policy-age <duration>` accepts 1 minute through 1 hour in whole seconds. A local-only home keeps its current file-load behavior and the `stale_after_days` advisory. The 14-day advisory does not control the hub freshness limit. Local control fits the trust model, which already trusts the owner of the home and their clock. Teams can distribute a tighter setting with their setup instructions. [Trust model](trust-model.md)

Measure age on the laptop's wall clock. Store `hub_confirmed_at` with the cached bundle in the same atomic write after a successful authenticated sync. Record the local time at the start of the successful policy fetch, so a slow response does not add time to the allowance. Bind the confirmation to the home configuration used for the fetch. Compare the origin, project, member, credential, and pinned keys at commit, and invalidate confirmation on any of those changes. An unchanged bundle at the version floor can refresh confirmation. A failed fetch, rejected bundle, or daemon restart cannot refresh it. A successful `policy load` from a file clears it. Old cached records have no hub confirmation and require a successful sync after upgrade.

A missing confirmation or one later than the current wall time is stale. Otherwise, subtract the confirmation from the current wall time. The policy is stale when that age reaches the limit. A backward clock adjustment that stays after confirmation reduces the measured age and can extend access in elapsed time. `policy status` shows the confirmed time, age limit, and state. It reads local state and makes no request.

On a stale policy-dependent hook call, try one direct sync per stale home using its configured hub. Use the same authenticated fetch, advertised and pinned key checks, version floor, and atomic admission as `policy sync` and the daemon. Give all attempts in one call a shared two-second budget, including network reads and any wait for a lock. Share the attempt per home with a bounded lock and recheck on-disk freshness after acquiring it. If a peer refreshed the home, use that policy. Back off for five seconds after a failed automatic attempt in that home. A manual `policy sync` can retry immediately. Reopen and recheck the policy before deciding. Release the home write lock during network I/O. Finish inside the existing four-second hook watchdog and five-second agent timeout. If budget runs out, emit the adapter's normal blocking response or exit 2 before the agent timeout. [Claude Code hook failure](hooks-claude-code.md#set-up) · [Codex hook failure](hooks-codex.md#what-the-hook-does-not-see)

| Action while the hub policy remains stale | Hook result |
|---|---|
| Write or `git.push` | Deny with a freshness reason and a `policy sync` recovery command. |
| Shell execution | Deny a matched shell call. Check freshness before using cached exec grants to choose the shell checks. The new policy could gate a command that the cached policy leaves alone. |
| Read that reaches the gate | Deny. A previously readable area could have become private. |
| Tool outside the adapter's coverage | Keep the adapter's existing scope. The freshness check cannot intercept a tool the agent never sends to the hook. |

A stale decision gets a local audit reason. Use the existing denial queue for an attributable policy action. `openplexer policy check` applies the same age rule to the diagnostic decision. Keep signature rejection and absent policy distinct from age. On a fresh policy, run the normal evaluator and require the existing decision audit append before allowing an action.

Add `openplexer policy check-session` for a startup check. For a stale connected home it attempts the same bounded sync and reports the result. The agent's `SessionStart` hook, where supported, uses the same check to show an actionable warning if policy is still stale. This leaves the session available for troubleshooting. The pre-tool gate checks age before each covered action throughout the session. A host without the session hook can run the CLI check and still gets per-call enforcement. The TypeScript reference at `7d80045a` checks signatures and versions at connect time and has a Claude Code startup hook. Phase 6 also needs a per-call check when the laptop starts without a daemon or a session stays open past the limit.

The v1 bundle has a policy `version` and can carry grant expiry times. Its protected header requires `alg` and `typ`. Both hubs also emit `kid` to identify the signing key. The v1 verifier accepts a header without `kid` when exactly one key qualifies and verifies the signature. Neither the v1 bundle nor the header defines an issue time. A signed issue time would reject an unchanged policy that the hub has just confirmed unless the lead reissued it. An added v1 payload field would still be ignored by old enforcement, and a v2 would require all verifiers to upgrade before reading it. Keep v1 bytes and signature rules. Existing bundles and verifiers remain compatible. Old clients continue their old advisory behavior until upgraded. The enforcement change is local to upgraded hub-connected homes. A warning or interactive ask for gated actions would still let a removed grant be used. The five-minute default measures recent contact in local wall time. The authenticated hub remains trusted to serve its current signed policy. [Policy signed bundle and compatibility](../spec/policy/README.md#the-signed-bundle)

## 8. Offline denial time (#97)

Use the `decided_at` contract owned by [#97](https://github.com/Multiplexer-si/OpenPlexer/issues/97). A queued denial retains its original local decision time through delivery and retry. The Phase 6 design relies on that field alongside the hub's receipt and audit times. #97 defines the field, compatibility, and conformance cases in its own change. Receipt time alone loses the time of a decision that waited in the outbox. [Room contract](../spec/room/README.md) · [Audit contract](../spec/audit/README.md)

## 9. Member sync state (#98)

Keep one latest record per active roster credential and project. Store `last_policy_fetch_at`, `policy_version`, and `last_room_connected_at` with nullable values. Set the fetch time and version when an authenticated `GET policy.bundle` selects a signed bundle for a `200`. Use the version of the signed payload being served. Set the Room time when the hub admits an authenticated live GET, or legacy Go POST, to a known Room. Record it once on the initial read, even when replay is empty. Stream polls, heartbeats, replay calls, HEAD requests, and failed authentication do not update it. These are server observations. A fetch does not prove the laptop received or verified the policy. A Room time does not indicate a current connection.

Keep just the latest value of each observation. Expire each observation after 30 days and delete empty rows. Suppress expired values at read time and purge them during hub maintenance. Delete the state on member removal. A new credential for the same member ID starts with empty state. Keep observations out of the audit chain. Use small writes in the Worker. On Go, keep the observations outside the main Room and audit snapshot so a policy poll does not rewrite the whole history. Coordinate observations with roster changes, so a late fetch or connection cannot restore a removed credential's state.

Both hubs serve lead-only `GET /api/v1/admin/members`. Use the auth, page size, and cache rules in section 1. Return `{members, next_cursor}`. Each row gives `member_id`, `hub_role`, `project_id`, and the three nullable observation fields. Return one row per member and project with retained observations. For a member with no observations, return one row with a null project ID. The optional `project_id` query returns one row per member for that project, including members without observations there. Use `404` for an unknown project. Page in member ID and project ID order. Use unpadded base64url of canonical JSON `[member_id, project_id]` for the `after` cursor and `next_cursor`. A malformed cursor gets `400`.

`openplexer-hub members` reads the Go data folder or uses `--hub` with lead credentials. It displays the observation times and version or `no recent observation` when the hub has no retained value. Multiple laptops for one member share that member's latest observations.

Use this exact note in [Architecture and privacy](architecture-and-privacy.md).

> The hub keeps the time and version of the last policy it served and the time of the last live Room connection it accepted for each member and project. Team leads and operators with access to the hub's data can see these values. They show hub activity and cannot confirm that a laptop applied policy or is still online. OpenPlexer stores no laptop identifiers, IP addresses, or per-request history in member sync state. Each value expires after 30 days. Removing a member clears that member's sync state.

A heartbeat from every laptop would add a device identity and a new activity feed. The existing authenticated requests give the lead enough information to follow up when a member may be out of date.

## 10. Admin dashboard (#99)

Serve a same-origin `/admin/` dashboard on the Worker. The Go hub keeps the shared invite and member APIs and CLI. The dashboard reads projects, roster and sync state, invites, current signed policy and version, Room replay, and the audit log. Show bounded Room and audit pages. Offer the existing signed audit export for offline verification.

A lead pastes the token on the HTTPS sign-in page. Submit it in the `Authorization: Bearer` header of a same-origin POST. The server verifies the lead through the same roster check as the API. Accept sign-in only from the exact configured `Origin` and with the expected JSON content type. Clear the browser input and its in-memory copy after submission. Keep raw tokens out of URLs, cookies, browser storage, logs, and HTML. Set `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on dashboard responses. Load scripts and styles from the same origin and use a content security policy that disallows framing and third-party code. Render Room and audit content as text.

Issue an opaque random session cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no `Domain`. Keep the session ID digest, member ID, enrollment ID from section 2, CSRF secret, and expiry server-side. Expire the session after eight hours and delete it on sign-out. Require the enrollment ID to match the active roster entry and recheck the lead role on each request, including at write commit. Refuse access after removal, token replacement, or loss of the role. Re-adding the same member ID and token hash leaves the old session invalid.

Require the exact origin and a session-bound CSRF value in a custom header on every session-authenticated mutation, including sign-out. Provide that value in a same-origin authenticated response. Reject missing or foreign origins and missing or invalid CSRF values. Keep GET and HEAD read-only and decline cross-origin API access. Dashboard cookie auth stays on dashboard handlers. The shared CLI API still uses bearers. The handlers call the same lead-authorized operations and record the same actor in audit.

A lead can add a project, create, approve, or revoke an invite, revoke a member, and publish a higher policy version through the existing policy checks. Confirm member revocation and show the role before issuing a lead invite. Keep Room and audit read-only. The CLI keeps bootstrap, signing key changes, and operator recovery. The invite view can copy the new join link once and keeps it out of browser history and persistent storage.

Serving the dashboard on both hubs would add a second browser session and asset stack. Starting with the Worker keeps one browser implementation and leaves Go operators the same onboarding operations through the CLI.
